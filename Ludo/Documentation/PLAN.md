## Architecture (proposed)
```
Presentation (Unity)   Views, UI screens, animations, audio playback      -> asmdef Ludo.Game (BoardView, TokenView, CameraFit)
Application / Flow     GameController (turn state machine), AI driver     -> Ludo.Game
Core rules (pure C#)   Board, Token, Dice, Rules, LegalMoves, GameState   -> Ludo.Core  (NO UnityEngine)
AI (pure C#)           IAiPlayer: Easy=random, Medium=priorities, Hard=Medium+danger/threat -> Ludo.AI
Services               AudioService, SaveService, AdsService (AdMob)      -> Ludo.Services
```
Rules: dependencies point downward only. Core never references UI/Ads/Audio/Scenes/Network. Views *observe* Core state via events; they never decide rules.

**Board model:** 52 outer cells (loop). Each token has player-relative `progress`: `-1` base, `0` own start cell, `0..50` outer track, `51..55` private home column, `56` finished. Absolute cell = `(startOffset[player] + progress) % 52` while `progress <= 50`. Safe cells = 4 start cells + 4 star cells (start+8). One `int` per token → deterministic, serialisable, testable, network-ready.

**Board grid:** `Core/BoardGrid.cs` maps every progress value to a point on the standard 15×15 grid (pure numbers, tested against the board image: start cells, star cells, home columns). `BoardView` multiplies by the cell size to get world positions. The board picture is scaled to exactly 15×15 world units (1.26×1.24 scale, ~1.8% non-uniform because the image is 1189×1210).

**Determinism:** dice comes from an injected `IDiceSource` (real random in game, scripted in tests, server value online).

**Turn state machine:** WaitingForRoll → Rolling → CheckingMoves → SelectingToken → Moving → Resolving → NextTurn (input accepted only in the states that need it).

**Rule variants** live in `RulesConfig` (plain serializable C# class in Core; a thin ScriptableObject wrapper is added in the Game layer in Phase 3 so you can tweak rules in the Inspector). Pause is a presentation concern (freeze input/time), not a Core rule; Restart = `LudoGame.Restart()`.

## UI design (Phase 5)

Every screen's content sits inside a `SafeAreaFitter` panel (Android draws edge-to-edge at target API 36); backgrounds fill the whole screen. `ScreenRouter` keeps a history stack: on-screen ◀ and Android Back both go back; Back on Main closes the app; Back in a game toggles Pause; Back on the result screen returns to the menu. `GameSession` (static) carries choices Menu→Game (reset on app start via `RuntimeInitializeOnLoadMethod`); `GameSettings` (PlayerPrefs) stores music/SFX volume, vibration, player names. ## AI design (Phase 4)
The AI gets `GameState` + the engine's legal moves and must return one of them (cannot break rules, cannot change the state; it clones to try moves). **Easy** = random. **Medium** = priority score: capture (60+½ victim progress) > reach home (70) > leave base (40) > enter home column (20) > safe cell (12) > progress. **Hard** = Medium score + 2.0×(danger removed) + 1.0×(threat created); *danger* = value of my unsafe loop tokens × (attackers within 1–6 cells / 6). Weights tuned by seeded tournaments (a pure-evaluation Hard was only ~47% vs Medium; the hybrid ~59%). Ludo is luck-heavy, so Hard's edge over Medium is modest; both crush Easy. If Hard needs to feel harder: add lookahead over the opponent's reply or per-opponent modelling (later, only if playtests ask for it).

## Audio, haptics & save design (Phase 6)

## Feature 1 — Realistic 3D physical dice (2026-09-23)
**Before:** `DiceView` = flat Kenney sprite that flickered random faces for 0.7 s then showed the value. The value was already decided by the engine (`LudoGame.Roll` via `IDiceSource`; online the HOST draws it with `RandomDiceSource`, broadcasts it, every phone pushes it into a `QueuedDiceSource`) — the view never decided anything.
**Now:** same authority, new presentation. `DiceSimulator` runs a real PhysX throw (Rigidbody + BoxCollider, mass/friction/bounce/damping, own gravity, continuous collision) in a **separate local physics scene** (floor + 4 invisible walls ±5.4 cells + dice only → cannot touch tokens/UI, no layers needed, global physics untouched), records it (60 Hz), and `DiceView` plays it back on the board (thrown from the roller's corner, random start/spin/spread, height = slight scale-up + moving soft shadow). The side physics leaves on top is found by dot product with world up (`UpAxis`, needs ≥0.985 = flat). The dice is then **relabelled** by one of the cube's 24 symmetries (`DiceMesh.Relabel`) so the engine's value is on that side — the dice lies exactly as physics left it, physics can never change the number. Leaning/too-long/outside throws are re-thrown invisibly (max 6); then a scripted tumble (always valid). After settling: 0.35 s on the board, slides back to the tray (value facing the player, tilted). Pause (timeScale 0) pauses it; restart/resync/exit call `Show()` which cancels it. All numbers configurable on `DiceView` (`DicePhysicsSettings`).
**Files:** `Game/DiceView.cs` (rewritten, same API + `PlayRoll(value, seat)`), `Game/DiceSimulator.cs`, `Game/DiceMesh.cs` (bevelled cube, opposite sides = 7), `Art/Dice/DiceShaded.shader` (unlit + fixed light, transparent queue, sorts with sprites), `Art/Dice/dice_faces.png` (`Prototype/make_dice_texture.py`, procedural, no third-party art), `Editor/DiceSetup.cs` (Ludo > Setup 3D Dice; run by Build Game HUD), `GameController` passes the seat. Online code unchanged (the number already arrives from the host).
**Measured:** 200/200 simulated throws landed flat in the arena, 0.8–2.6 s (avg 1.4 s), farthest 3.8 cells from centre, ~6 ms per throw (Editor PC). Tests: relabel for every value × side, 500 random landings show the engine value, mesh closed/outward, opposite sides = 7.

## Rank / XP / rewarded-ad / disconnect system — built 2026-09-22 (189/189 tests)

**Deliberate departures from the reference (each one is a "do not fake it" call, not an oversight)**
- **Gems, Lucky Spin, Clubs, Season Pass, timed events** — drawn in the art, no system behind any of them. Left out instead of shown as controls that do nothing.
- **Bottom nav sits ~196 px above the screen edge**, not flush. The main menu carries an AdMob banner there and the ads policy forbids tappable UI against it; the project already moved buttons off that edge for this reason.
- **Profile has no bottom nav** — the reference's profile uses that space for its own Statistics/Rewards/Achievements tabs. There is no achievements system, so the page is one honest page, and dropping the bar is also what lets every number fit a 16:9 screen.
- **Select Mode has no Arrow row** (the reference has none) although the game has Arrow mode; it stays selectable on the Play Online and vs Computer mode chips.
- **Play Online's tile grid trimmed to the reference's four cards** — Leaderboards and Profile moved to the bottom bar, the account to the header gear, the dice collection to the main menu, so nothing became unreachable.

**Gap analysis (what the reference adds that the project does not have yet)**
- *Structure:* a persistent **bottom navigation bar** (Home / Friends / Chat / Profile) on the menu screens; the current build has no bottom nav at all.
